# CLAUDE.md

## Project

Arcade Vault ("Es una plataforma para jugar online y competir por la mayor cantidad de puntos") is a Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 project. It is a visual/mock port of the `references/templates/home-about` reference template — see `specs/` for what has been implemented so far and in what order.

Current routes: `/` (Home landing), `/games` (Biblioteca), `/games/[id]` (Detalle), `/games/[id]/play` (Reproductor), `/login` (Auth), `/hall-of-fame` (Salón de la Fama), `/about` (Acerca de + formulario de contacto). See `implemented-games.md` for the current list of games wired into the catalog and playable (six as of this writing: `asteroids`, `tetris`, `arkanoid`, `snake`, `crossing`, `invasion`; update that file, not this one, whenever a game is added — see `.claude/skills/add-game/recipe.md` for how a game plugs in). The game catalog and scores are backed by real Supabase (`lib/supabase/client.ts` / `server.ts`; `lib/data/games.ts` reads the `games_with_stats` view and reexports the shared types it gets from `app/data/games.ts` (`Game`, `GameWithStats`, `ScoreRow`, `CATS`); `lib/data/scores.ts` inserts into `scores`) — only the user session (`av_user`) is still mocked via `localStorage`, not auth. The UI has an ES/EN language selector (`lib/i18n/language-context.tsx`, persisted to `localStorage` as `av_lang`, dictionary in `lib/i18n/translations.ts`); game catalog text falls back from `title_en`/`short_en`/`long_en` to the Spanish columns via `lib/i18n/localize-game.ts` when a translation is missing. `app/actions/` holds two Server Actions: `contact.ts`, whose email send is mocked (see `.env.example` for the Resend-shaped env vars it is written against, none of which are read yet), and `hall-of-fame.ts` (`fetchTopScores`), which is real and reads from Supabase like the rest of the catalog/leaderboard data.

## Next.js version warning

`package.json` pins `next@16.2.10`, which is **not** the Next.js you know from training data — APIs, conventions, and file structure may differ. Before writing or changing any Next.js-specific code (routing, data fetching, config, metadata, images, fonts, etc.), read the relevant page under `node_modules/next/dist/docs/` (organized as `01-app/`, `02-pages/`, `03-architecture/`, `04-community/`) rather than relying on prior knowledge. Pay attention to deprecation notices there. The same warning is duplicated in `AGENTS.md` at the repo root.

## Spec-driven workflow

This repo works by spec, not by ad hoc prompting. Four project skills drive it, all human-only (`disable-model-invocation: true`, not invocable by the model on its own) — defined in `.claude/skills/`, full contract in each one's `SKILL.md`:

- **`/spec`** — designs a new feature spec interactively, section by section against `.claude/skills/spec/template.md`, and saves it to `specs/NN-slug.md` in `Draft` state. Never writes code.
- **`/add-game`** — the same thing, specialized for adding one playable game (plus its leaderboard) to the catalog, either porting existing code from a folder (e.g. `references/started-games/`) or designing it from scratch. It already knows the wiring recipe (`.claude/skills/add-game/recipe.md`: the manual `insert into games` SQL, `.cover-<id>`, `components/games/<id>/engine.ts`, `components/games/<id>-player.tsx`, the branch in `app/games/[id]/play/page.tsx`). Also ends at `specs/NN-slug.md` in `Draft`, never writes code. Use it for a new game; use `/spec` for anything else.
- **`/spec-impl`** — implements a spec, but **only if its status line reads `Approved`** (or an equivalent word in another language). It creates/switches to a branch named `spec-NN-slug` (see `AutoCreateBranch` in `specs/.spec-config.yml`, default `true`), then implements the plan one step at a time, pausing for review after each step.
- **`/spec-impl-game`** — a wrapper for specs that add a playable game to the catalog. `/spec-impl` stays deliberately human-only, so this command never invokes it as a skill; instead it reads `.claude/skills/spec-impl/SKILL.md` as text and carries out its documented phases itself. Once that reaches its own successful end, it automatically chains the `skin-designer` agent, then, once that reports back, the `mobile-porter` agent (skipping it with a note if the game is one of the four spec 12 already migrated), then, once that reports back, the `game-performance` agent — all three onto the game that was just implemented. Never runs two of these agents in parallel — all three edit the same `-player.tsx` file. Use it for game specs; use plain `/spec-impl` for anything else.

A fifth skill, **`frontend-design`** (`.claude/skills/frontend-design/`), is a vendored copy of Anthropic's stock skill (see `skills-lock.json`) — the only one of the five that is model-invocable, not human-only. See the `## Skills` note below.

Five custom agents feed into this workflow, defined in `.claude/agents/`, full contract in each one's `.md` file:

- **`game-planner`** — answers the question that comes _before_ `/add-game`: given the current catalog, what game should be added next? It diagnoses gaps (category, mechanic, control scheme) against `implemented-games.md`, researches candidates, scores them against fit criteria, and proposes 1–3 ranked options. It keeps memory of every candidate it has evaluated — proposed/accepted/rejected/deferred — in `suggested-games.md`, so it never re-proposes something already built or already turned down. Never writes code or specs; the human decides, then runs `/add-game <chosen game>`.
- **`game-jam`** — takes a theme or a named game and, without asking any clarifying questions, writes **two alternative specs** for the same game concept into `specs/game-jam/NN-slug.md` (its own sequential numbering, separate from `specs/`), each differing along one declared axis (fidelity, scope, mechanic, or category) and each with its own `id`. It reads `implemented-games.md` and `suggested-games.md` to avoid collisions but never writes to them. Never writes code; the human picks one spec, promotes it into `specs/NN-slug.md`, flips its status to `Approved`, and runs `/spec-impl`.
- **`skin-designer`** — **writes code**, the deliberate exception to "agents never write code." Given ONE game named explicitly, it audits that game's `engine.ts`/`-player.tsx` for skin coverage and edits them directly (plus the shared `lib/skins.ts` / `components/skin-selector.tsx` it maintains) so it offers at least the `clasico` (default), `neon`, and `retro` skins, legible against the site's permanently dark background. It refuses to sweep the whole catalog on its own. Doesn't go through `specs/` or `/spec-impl` — there's no spec-then-approve gate for it, since skin work is scoped, visual-only, and reversible per game.
- **`mobile-porter`** — **writes code**, another deliberate exception, this one for touch/mobile support on ONE explicitly named new game. It wires the pattern `specs/12-juegos-en-movil-tactil.md` established (shared `<TouchPad>`, `<HudMenu>`, `lib/canvas-hidpi.ts`, and pointer-drag where warranted). The four games spec 12 already migrated (`asteroids`, `tetris`, `arkanoid`, `snake`) are out of scope by design — they already work as expected.
- **`game-performance`** — **writes code**, a third exception, this one for runtime performance on ONE explicitly named game. It audits `engine.ts`/`-player.tsx` against the antipatterns `specs/14-rendimiento-cruce.md` diagnosed and fixed in `crossing` (a fully redrawn static background instead of a cached offscreen canvas, unstable-identity props defeating the `React.memo`-wrapped `<TouchPad>`/`<HudMenu>`/`<SkinSelector>`), measures with an automated Playwright session when a dev server is available, and applies the same fix pattern. Unlike `mobile-porter`, it has no legacy-game exclusion list — every game, including the four spec 12 already migrated, is a valid target.

Implications for any work in this repo:

- A feature-sized change should normally go through `specs/NN-slug.md` first, not straight into code. If asked to build something nontrivial without a spec, point this workflow out.
- Never implement a spec whose status isn't `Approved` (or a same-meaning word in another language) — that gate is intentional and enforced by the human, not by the agent.
- Spec status values: `Draft` → `In review` → `Approved` → `Implemented` → `Obsolete` (or the equivalent terms in whatever language the repo's specs use — stay consistent with what's already there).
- Numbering is sequential (`01-`, `02-`, ...); `specs/` currently runs `01`–`22`, so the next free number is `23`. `specs/game-jam/` numbers separately and holds unpromoted alternatives (currently `02`, `04`, `05`, `06` in `Draft` — `01` and `03` were promoted into `specs/16-` and `specs/15-` respectively). Check both before creating a new spec.

## Architecture notes

- App Router only (`app/` directory) — there is no `pages/` directory.
- Styling is Tailwind CSS v4 via `@tailwindcss/postcss` (see `postcss.config.mjs`), plus `app/globals.css`.
- Path alias `@/*` maps to the repo root (`tsconfig.json`).
- `eslint.config.mjs` uses the flat config format (`eslint/config` + `eslint-config-next/core-web-vitals` and `eslint-config-next/typescript`), not the legacy `.eslintrc`.
- A `PostToolUse` hook (`.claude/settings.json`, matching `Write|Edit`) runs `eslint --fix` on touched JS/TS files and then `prettier --write` on every touched file automatically — no need to invoke either by hand after an edit.
- Reference templates the specs port from live in `references/templates/` (plain React-via-CDN `.jsx`/`.css`, not part of the Next.js build) — consult them for markup/CSS fidelity, but never import them directly. `references/` also holds `started-games/` (candidate code for `/add-game` to port), `snake-assets/`, and `gamepad-assets/`.
- `@supabase/supabase-js` + `@supabase/ssr` are real dependencies (`lib/supabase/`); games/scores data flows through Supabase, not local mocks — see `specs/04-supabase-integration.md` and `specs/06-leaderboard-catalogo-supabase.md`.
- There are two Supabase projects: dev (the one `.mcp.json` and Claude Code's MCP access point at) and a separate production project Claude Code has no access to — see `specs/23-migracion-a-produccion.md`. `db/prod/01-baseline.sql` is the canonical, idempotent transcription of the current `public` schema (kept in sync by hand whenever a spec adds DDL — the individual specs' inline SQL snippets can drift out of sync with each other and with the live schema); `db/prod/02-seed-games.sql` seeds the games catalog; `db/prod/03-verificacion.sql` is the post-migration check.
- Each game's engine (`components/games/<id>/engine.ts`) is pure TS with no JSX/React; the `"use client"` player wrapper (`components/games/<id>-player.tsx`) is the only piece that touches React and `localStorage` (session read, per-game sound/skin prefs).
- Every game consumes the same shared, cross-game infrastructure rather than reinventing it per game (specs 12/13): `components/games/touch-pad.tsx`, `components/games/hud-menu.tsx`, `lib/canvas-hidpi.ts`, `lib/skins.ts`, and `components/skin-selector.tsx`. Treat these as fixed contracts to consume — `mobile-porter` and `skin-designer` are the only agents that touch them, and even they only extend them, not redesign them, as part of a single-game run.
